## 🔴 MASALAH YANG DITEMUKAN

Setelah pengujian end-to-end langsung di produksi (`pilih.ammang.my.id`), ditemukan 4 masalah kritis pada flow pembayaran QRIS:

### 1. Tidak Ada Waktu Expired QRIS
- Vendor ID 14 & 15 (`qris-test-1785837731@ammang.test`, `test123@ammang.test`) terdaftar dengan status `pending_payment`
- **Tidak ada `expiresAt`** untuk pembayaran QRIS - data akan nyangkut selamanya
- Field `expiresAt` di tabel `vendors` HANYA untuk langganan bulanan (30 hari), bukan untuk sesi pembayaran
- User vendor tidak melihat countdown/timer expired QRIS di UI

### 2. Data "Zombie" Menumpuk di Database
- Jika user tidak membayar QRIS, datanya tetap ada di `vendors` dengan status `pending_payment` selamanya
- Tidak ada mekanisme auto-cleanup / archive
- Admin dashboard menampilkan vendor "pending" yang sebenarnya sudah tidak relevan

### 3. Alur Batal & Ganti Plan Tidak Jelas
- Scenario: User pilih **Plan 3 (Business)** dengan QRIS → belum bayar → ingin **batalkan** dan **ganti ke Plan 2 (Pro)**
- **Tidak ada mekanisme**: user tidak bisa cancel order QRIS yang pending
- **Tidak ada regenerasi QRIS**: user tidak bisa request QRIS baru untuk plan baru
- **Tidak ada popup payment** yang mengatur alur ini

### 4. Tab UI Masih Gabung
- Tab "Menunggu Konfirmasi" menampilkan campuran QRIS (`pending_payment`) dan Manual (`pending_manual`) bersamaan
- Belum ada pemisahan visual yang jelas antara "Menunggu Pembayaran QRIS (Otomatis)" dan "Menunggu Konfirmasi Manual"

## 💡 SOLUSI YANG DIREKOMENDASIKAN

### A. Buat Tabel Baru: `payment_sessions`

**Alasan**: Jangan campur data sesi pembayaran sementara dengan data vendor permanen. Pisahkan agar:
- Mudah tracking masa expired QRIS per transaksi
- Mudah cleanup data kadaluarsa
- Data vendor hanya dibuat permanen SETELAH payment sukses

```sql
CREATE TABLE IF NOT EXISTS payment_sessions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  orderId TEXT NOT NULL UNIQUE,          -- ORDER-{timestamp}-{vendorId}-{random}
  vendorId INTEGER NOT NULL,              -- referensi ke vendors.id (draft)
  planId INTEGER NOT NULL,                -- plan yang dipilih
  amount INTEGER NOT NULL,                -- nominal pembayaran
  status TEXT DEFAULT 'pending',          -- pending | paid | expired | cancelled
  paymentMethod TEXT DEFAULT 'qris',      -- qris | manual
  qrUrl TEXT DEFAULT '',                  -- URL QRIS dari Midtrans
  expiresAt DATETIME NOT NULL,            -- WAKTU EXPIRED QRIS (default: now + 2 jam)
  createdAt DATETIME DEFAULT CURRENT_TIMESTAMP,
  paidAt DATETIME,
  rawResponse TEXT,
  FOREIGN KEY (vendorId) REFERENCES vendors(id)
);
```

### B. Alur Baru (Sesuai Standar Payment Gateway)

```
1. User pilih plan (misal Plan 3 - Business)
2. User isi data diri (email, nama, whatsapp) → CREATE draft vendor dengan status 'pending_payment'
3. System panggil /api/payment/create → Midtrans QRIS
   → Response: { qrUrl, orderId, expiresAt }
4. System SIMPAN ke payment_sessions:
   → orderId, vendorId, planId, amount, expiresAt = now + 2 JAM
5. UI tampilkan QRIS + COUNTDOWN TIMER (expiresAt)
6. User scan & bayar dalam 2 jam
7. Webhook Midtrans 'settlement' diterima → 
   → UPDATE payment_sessions SET status='paid', paidAt=now
   → UPDATE vendors SET status='active', planId=..., expiresAt=now+30hari
   → Kirim email aktivasi
8. Jika EXPIRED (2 jam habis):
   → UPDATE payment_sessions SET status='expired'
   → UPDATE vendors SET status='expired_draft' (atau HAPUS draft)
   → UI vendor: tampilkan "QRIS Expired" + tombol [Bayar Ulang] / [Ganti Plan]
```

Buat **PaymentModal** component yang mengatur seluruh alur pembayaran:

```

│─────────────────────────────────────│
│  Paket: Business Studio Plan        │
│  Harga: Rp 199.000                  │
│                                     │
│  [QRIS CODE IMAGE]                  │
│                                     │
│  ⏰ Sisa Waktu: 01:59:32            │
│                                     │
│  [🔄 Ganti Paket]  [❌ Batalkan]    │
└─────────────────────────────────────┘
```

**Fitur yang harus ada di modal:**
1. **Countdown Timer** - hitung mundur dari `expiresAt`
2. **Tombol Ganti Paket** - redirect ke halaman pilih plan, cancel session lama
3. **Tombol Batalkan** - cancel order, hapus/arsipkan draft vendor
4. **Auto-Refresh Status** - polling `/api/payment/status` tiap 5 detik
5. **Status Expired** - tampilkan pesan "QRIS Kadaluarsa" + opsi regenerate

### D. API Endpoint Baru yang Dibutuhkan

| Endpoint | Method | Fungsi |
|----------|--------|--------|
| `POST /api/payment/create` | POST | Buat sesi payment + QRIS baru (sudah ada, perlu tambah expiresAt response) |
| `GET /api/payment/session?orderId=...` | GET | Ambil status sesi payment (untuk polling UI) |
| `POST /api/payment/cancel` | POST | Batalkan sesi payment pending (untuk tombol "Batalkan") |
| `POST /api/payment/regenerate` | POST | Generate ulang QRIS baru (untuk tombol "Bayar Ulang") |
| `POST /api/payment/change-plan` | POST | Ganti plan pada sesi pending (untuk tombol "Ganti Paket") |
| `POST /api/payment/notification` | POST | Webhook Midtrans (sudah ada, perlu handle status expire juga) |

### E. Cleanup Otomatis (Cron/Interval)

**Opsi 1: Interval di lib (lebih simpel)**
```js
// Di lib/vendor-status.js atau file baru lib/payment-cleanup.js
setInterval(() => {
  const expired = db.prepare(`
    SELECT * FROM payment_sessions 
    WHERE status = 'pending' AND expiresAt < datetime('now')
  `).all();
  
  expired.forEach(session => {
    db.prepare(`UPDATE payment_sessions SET status='expired' WHERE orderId=?`).run(session.orderId);
    db.prepare(`UPDATE vendors SET status='expired_draft' WHERE id=?`).run(session.vendorId);
    console.log(`[Payment Cleanup] Session ${session.orderId} expired`);
  });
}, 60 * 1000); // cek tiap 1 menit
```

**Opsi 2: Cron job PM2 terpisah**
```bash
# Di ecosystem.config.js PM2
{
  name: "payment-cleanup",
  script: "scripts/payment-cleanup.js",
  cron_restart: "*/5 * * * *"  // jalan tiap 5 menit
}
```
